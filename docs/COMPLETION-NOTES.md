# 完成說明

## 做了什麼

依 spec 與八張 ticket 的切片順序,把原本單檔的 LINE 機器人(Google Apps Script)重寫完成,每張 ticket 都是「Webhook 進、LINE reply 與狀態出」的垂直切片,並以 TDD(紅 → 綠 → 重構)完成:

1. **骨架**:假的 GAS 世界測試台、守門(網址密鑰、事件去重、白名單、陌生人只回 ID)、狀態儲存(試算表 + 快取 + 全域鎖 + 單格 50,000 字元分塊)、Gemini 呼叫(標頭金鑰、時間預算、429/5xx 重試一次、錯誤分類只看狀態碼與結構化欄位)、reply 失敗處理與有月預算的 push 補送、日誌批次寫入與輪替、設定預設值與範圍檢查。
2. **回覆格式化**:Markdown 轉純文字、依 LINE 限制在自然邊界分段(每則 ≤5000 字、最多 5 則)。
3. **時間感知**:時段、與上一則訊息的間隔分級、「(距上一句約…)」註記。
4. **搜尋加固**:`web_search` / `web_fetch` 工具迴圈(並行 `fetchAll`、強制作答)、搜尋結果清洗與注入警報、一次性標記資料區塊、讀頁網址白名單、使用者明令搜尋(跳過第一輪模型)、深入模式(讀頁 + 無人設輔助模型摘要)、汙染回合標記。
5. **圖片先傳後問**:單獨傳圖只回「收到,想問什麼?」,10 分鐘內的下一則文字現場下載並內嵌。
6. **群組**:只在被 @ 時回應、整個群組共用一份對話並與個人完全獨立、群組白名單、群組傳圖靜默暫存。
7. **記憶**:整理(日誌事件 + 完整新版長期事實 + 歸檔)、常駐注入、bigram 檢索、`/記憶`、`/忘記`(二次確認、物理刪除)。
8. **生圖**:`generate_image`(Cloudflare → Drive → 單一 reply)、全域每日額度/冷卻/暫停、Cloudflare 錯誤碼處理、Drive 保留期清理(圖片只存在 `IMAGE_DRIVE_FOLDER_ID` 指定的專用資料夾,清理也只處理該資料夾內的檔案)、圖片網址健檢維護函式。

另外提供維護函式 `setupSheets`、`smokeTest`、`checkImageUrls`、`refreshUsersCache`。

**統計**:`src/` 約 2,300 行、19 個檔案;330 項測試(`npm test`)。每張 ticket 完成後我都對關鍵邏輯做突變檢查(刻意破壞程式碼,確認測試會轉紅),過程中抓到並補上了數個測試缺口,也抓到並修正了幾個真實的瑕疵(見下)。

## 尚未在真實環境驗證的部分

**全部測試都只在假的 GAS 世界中通過,沒有任何真實連線。** 我沒有 LINE、Gemini、TinyFish、Cloudflare、Google 帳號。具體來說以下都只在假的服務上驗證過,必須照 `MANUAL-ACCEPTANCE.md` 在真實環境確認:

- Apps Script V8 的執行期相容性(正規表示式 lookbehind 與 `\p{L}`、`Utilities.formatDate`、`ContentService` 等)→ 先執行 `smokeTest`。
- 真實的 LINE webhook 行為(重送、`mention` 提及資訊的 `index`/`length` 單位、群組事件欄位)。
- Gemini 的結構化輸出(`responseJsonSchema`)與函式呼叫在真實模型上的行為,以及輔助模型是否真的產出合法的整理結果。
- Cloudflare 回應格式與錯誤碼、Drive 設定分享、`lh3.googleusercontent.com/d/{id}` 與 `drive.google.com/thumbnail` 兩種網址是否仍能在 LINE 手機端顯示(Google 未正式承諾)。
- 試算表與快取的真實延遲:**冷啟動時第一次開啟試算表的實際耗時**(用 `DEBUG_TIMING` 量測,決定是否要再合併讀取階段)。
- 真實併發(本專案以「在 Gemini 呼叫期間巢狀處理另一個請求」模擬交錯,不等於真正的多執行緒)。

## spec 沒寫到、由我自行決定的細節

**錯誤與時間預算**
- 錯誤句對應:429 或 5xx 重試後仍失敗 →「太忙」;網路例外/逾時/預算不足 →「逾時」;400 與其他 →「一般錯誤」;安全擋下 →「被擋下」。
- 單次 Gemini 呼叫上限 40 秒;重試退避 1 秒,且退避後仍須剩下至少 3 秒才重試。出錯的回合不寫入歷史。
- 缺 Gemini 金鑰時回固定說明;`Users` 表「啟用」欄空白視為停用。
- 設定與日誌的限頻:缺金鑰/設定值不合法每小時最多記一次;`BAD_KEY` 每 10 分鐘一次;陌生人同一 ID 每小時一次。

**回覆與格式**
- 歷史保存「使用者實際看到的純文字」(已轉 Markdown),避免把 Markdown 餵回模型。
- 截斷標示「…(內容過長)」佔用最後一則的字數額度。

**搜尋**
- 同一輪最多執行 4 個函式呼叫;查詢字串須 ≥2 字;TinyFish 搜尋 15 秒/讀頁 25 秒單次上限(同樣受剩餘預算限制);搜尋失敗不重試。
- 讀網頁白名單 =「本輪(同一請求)搜尋結果中、已通過清洗/封鎖/注入過濾」的網址,再加上 https 公開網域檢查。
- 注入警報、清洗的 HTML 標籤判斷與參考實作略有不同(只認 `<` 後接字母、`/`、`!`,避免 `3 < 5 且 7 > 2` 被整段吃掉)。

**圖片**
- 圖片 ack(「收到,想問什麼?」)不用 push 補送(節省預算),但即使 reply 失敗圖片仍被記下。
- 圖片下載失敗或過大時,在回覆後附註,並在 system prompt 告知模型看不到圖;這些圖視為已消耗(使用者需重傳)。
- 歷史前綴「[圖片] 」只在至少一張圖成功帶上時加。
- 已知限制:未限制單次請求內嵌圖片的總大小(Gemini 內嵌請求約有 20MB 總量上限);`fetchAll` 若發生網路層例外,整批視為失敗。

**群組**
- 只有 @ 沒有內容 → 靜默忽略。群組 system prompt 多一句「多人共用、不知道誰說的」。
- `/忘記` 的確認旗標以「聊天室 + 發送者」為鍵(別人輸入只是自己的第一次);未登記群組傳圖完全忽略。

**記憶**
- 整理在 reply 之後、取鎖之前呼叫模型,結果與本回合在**同一個寫入階段**寫入(因此一個請求至多一次取鎖,也不會有「事件寫了但進度沒前進」造成重複的問題);若期間 State 最舊的原文已變動(例如被 `/忘記`),整份結果作廢(`FOLD_STALE`)。
- 一次整理最舊 `min(FOLD_BATCH_TURNS, 輪數−1)` 輪(至少留 1 輪原文);整理用的 `maxOutputTokens` 固定 4096(不受對話用的 `MAX_OUTPUT_TOKENS` 截斷)。
- 整理一直失敗時 State 的原文有安全上限(`HISTORY_MAX_TURNS` 的 3 倍,超過丟最舊並記 `HISTORY_CAP_DROP`)。
- 歸檔每筆在檢索快取裡截 300 字;語料超過 90KB 不放快取(每次讀表)。從未整理過的聊天室完全不讀 Events/Archive。
- 檢索標籤:「長期記憶」「日誌」「更早的對話·使用者/我」(沒有角色人設)。
- `/記憶`、`/忘記` 的回覆不用 push 補送、不寫歷史、不更新最後互動時間;指令比對容許前後空白,但其餘須完全符合(`/忘記嗎` 不是指令)。

**生圖**
- 圖片額度、冷卻、暫停是三種獨立狀態;函式只在「當下可用」時才宣告,執行時再檢查一次;失敗與成功都以「回覆後附註」告知使用者,同時告知模型不要編造。
- `_system` 列不存在時也做負向快取,熱請求才不會因為檢查額度而讀試算表。
- 提示詞本地先檢查 ≤2000 字(超過直接拒絕,不浪費請求),Cloudflare 回 3006 時同樣告知「提示詞太長」。

## 修正的真實瑕疵(測試過程中發現)

- 鎖內快取沒命中時,若沿用請求開頭讀到的表格快照,會覆蓋另一個請求剛寫入的回合 → 改為鎖內重新讀取(有兩項併發測試守住)。
- 參考實作的 `left_out_fact_lines` 以「區段 + 內容」判斷是否已顯示,內容重複的行會被誤判 → 改為依位置判斷。
- 替換程式區段時誤刪常數導致「缺 Gemini 金鑰」的回覆失效 → 被既有測試抓到(也驗證了最外層的例外攔截會留下 `UNHANDLED` 日誌)。
- 使用者內容會寫進 Archive/Events:若以 `=` 開頭,試算表會當成公式(可被利用外流資料)→ 兩張表建立時設為純文字格式,測試台的假試算表會在非純文字表寫入 `=+-@` 開頭字串時直接丟錯。

## spec 內部矛盾或與原程式衝突之處(以〈Implementation Decisions〉為準)

- 「冷路徑至多 2 次讀取階段」:我把「使用者、狀態、事件、歸檔」四次連續的讀取視為一個讀取階段(`w.readPhases()` 以「彼此相連、中間沒有寫入/外部呼叫/取鎖的讀取」計算),因此冷請求的讀取階段不超過 2;實際的 `getValues` 次數在有整理過的聊天室冷請求時可到 4 次。冷啟動第一次開啟試算表的耗時需在真實環境量測。
- 「每個請求至多一個寫入階段」與「整理在 reply 之後執行」:以「整理的模型呼叫不持鎖,結果與本回合同一個寫入階段」調和。
- 原程式的「單獨傳圖就立刻描述」已依 spec 移除(有測試守住)。
- spec 的 `Users` 表種類:群組填 `group`;我同時接受 `room`(與 group 視為同類)。

- 突變檢查:每張 ticket 完成後,我手動破壞數十個關鍵邏輯點(白名單判斷、鎖內重讀、分塊上限、重試、強制作答、讀頁白名單、額度/冷卻/暫停、`/忘記` 的比對與清除範圍等),確認測試會轉紅;沒被抓到的突變若不是等價突變,就補上測試。
